# Slopbot public guide

This guide ships with each build. It describes implemented behavior and known limits, not live health. Update it when behavior changes. Other architecture documents include historical proposals.

## overview
Slopbot is a TypeScript Discord assistant for shared discussion, source-backed history retrieval and sustained tasks. Mention it or reply to it in an allowed channel. Ordinary channel requests are fresh runs with selected context. Bot-created task threads retain an ordered conversation. Ask for history searches, source quotes, web searches, summaries, polls, tasks or reminders. Server configuration changes require Manage Server permission. Ask bot_info for a specific topic before explaining internals.

## architecture
Application validates and ingests requests and serializes task contributions. ContextBuilder selects references, recent messages, profiles and recall within a budget. AgentRunner drives the model/tool loop and harness state machine, retains provider events, checks context versions and creates checkpoints. ToolRegistry validates arguments and permissions, journals operations and coordinates writes. Discord adapters normalize events and deliver replies. Presentation modules handle Discord formatting, names, link previews and tool progress. LLM, database, search and file adapters are replaceable interfaces. Source: architecture/IMPLEMENTATION.md and HARNESS.md.

## context
Channel replies do not resume an old session. They include the new message, referenced evidence, selected recent chat and relevant stored information. Task threads replay saved prompt snapshots and append new attributed turns; concurrent inputs are ordered. Context is bounded, so indexed history is not all inserted into every request. Task checkpoints retain original history and provider-exposed reasoning in storage. Raw reasoning deltas are retained but not replayed as ordinary chat. Edits, deletions and excluded channels invalidate affected derived context. Source: architecture/CONTEXT.md.

## memory
Canonical messages use Discord message IDs to prevent duplicate ingestion. Live ingestion stores new messages from configured channels; historical imports fill a time window and can continue further back. Older imports remain stored. Search combines scoped keyword/full-text and semantic retrieval; PostgreSQL uses pgvector, SQLite scans vectors locally. Embeddings are model-specific and separate from the reply model. history_search finds evidence; history_read reads surrounding messages and reply ancestors. Profiles tie Discord identities and attributed fields to users. Reports link sources and reject stale evidence. Coverage and indexing status describe what is available, not complete access to all Discord history.

## tools
Slash commands and LLM calls use one ToolRegistry with the same validation and authorization. Users need not manually invoke tools if the bot can select them. Reads can run inline; sustained writes can move to task threads. Tool intent/results are journaled; uncertain external results require reconciliation before retry. Discord shows execution progress and a final tool footer. Structured UI uses a validated versioned JSON document and registered actions, never generated executable code. Components support cards, buttons and selects; polls use native Discord polls. Tasks track goals, owners, progress and questions; reminders are persisted. Use capabilities for the current registered tool names.

## deployment
Production runs in a PMServers container with managed PostgreSQL/pgvector. SearXNG runs as a separate private service. The bot uses SEARXNG_MODE=external; a transitional Tailscale bridge provides development search access. GitHub Actions tests main pushes, builds a multi-architecture GHCR image and deploys it to PMServers. The managed database persists across container replacement. Development uses its own Discord application and isolated Postgres schema, reaching PostgreSQL through the PMServers SSH database tunnel and search through the transitional private bridge. Protected HTTPS search supports Cloudflare Access headers, but its cutover awaits PMServers token-retrieval support. A schema is not a database permission boundary. Credentials stay outside source control and are not exposed by this tool. This describes topology, not current deployment success or service reachability. Source: architecture/DEPLOYMENT.md and DEVELOPMENT.md.

## caching
Fixed system instructions and deterministically serialized tools come first. Changing context follows. Task turns and tool rounds append without rewriting earlier prompt items. Large new tool evidence is shortened before insertion; full results remain stored. If new evidence cannot fit, execution stops instead of dropping earlier items mid-round. Checkpoints, source invalidation or changed instructions legitimately start a new cache prefix. Gateway usage reports actual cached tokens; hashed client diagnostics track prompt stability separately. Provider routing, prefix thresholds and eviction mean a cache hit cannot be promised on every call. Source: architecture/PROMPT_CACHING.md.

## timing
The timing tool toggles server-wide timing footers and requires Manage Server permission. It defaults to off. Footers report reference fetching, participation checks, queue wait, context, model streaming and tool durations before Discord delivery. JSON logs and saved timing records include full total and delivery time. Use timing_inspect on a replied-to bot response or request to explain its actual measurements; only the current permitted channel is accessible. Each tool invocation shows its name in backticks, status and duration, including in progress updates. Saved tool results do not invent an original duration. First model output can include reasoning or tool output and is included in model time. Checkpoint time overlaps context; other covers remaining work. Measurements are process-local during execution and persisted after delivery; recovered jobs are marked partial. Old requests may lack stored timing. Timings identify slow stages, not prove root causes. Collection does not change prompts or cache behavior. Source: architecture/TIMING.md.

## limitations
Timing interpretation: first output marks only the beginning of streamed output. Later elapsed time can include continued model generation, provider/network wait and journal writes. Never infer that all time after first output is I/O. Nested journal/classifier timings are not additive. Participation can wait behind earlier channel checks. Streamed events are batched without merging or discarding raw reasoning; final/error flush is awaited, but an abrupt process termination can lose pending buffered events.

The reported real-Discord GIF/attachment failure remains unresolved. File readers exist, but the bot must not claim every attachment or model supports vision. Indexing may be incomplete; inspect coverage before making claims about a person's full history. Source-backed search is evidence retrieval, not perfect recall. Automatic topic grouping and cross-server profile sharing are deferred. Unknown names and conflicting task instructions may require clarification. Live health and deployment state require separate operational checks; this guide cannot prove them. Discord does not render Markdown tables; presentation converts them to lists and suppresses multiple-link previews by default.

## observability
The revised collector tracks actual client await boundaries in request-scoped async context. It separates database connection queue from SQL operations, model headers from stream reads, and participation queue from classifier work. Search, embeddings, resource locks, worker queues and Discord sending have labels. Concurrent outstanding awaits form one non-overlapping interval, so wall-clock wait buckets reconcile to total; stage durations remain overlapping diagnostics. Application/uninstrumented is a coverage gap, not a claimed service bottleneck. A provider wait cannot reveal GPU computation or separate server time from network/event-loop delay. SQLite synchronous work is currently uninstrumented. Use timing_active for other active requests in this permitted channel, or timing_inspect view=timeline with offset for ten saved intervals at a time. A watchdog logs current waits for slow requests every 15 seconds, even if workers are busy; it cannot run during a blocked event loop. Timelines retain the last 256 intervals; aggregate combinations are bounded and truncation is explicit. Old records do not acquire detail retroactively. Diagnostic storage is after delivery and excluded from response latency. Prompt contents and cache behavior are unchanged by collection.

## other_bots
Other bots and webhook apps in configured channels are ingested as source-linked context, including embed titles, descriptions and fields. Other bots follow the same participation rules as users: mentions, replies to Slopbot and task-thread messages trigger responses; ordinary messages use monitoring when enabled. Bot-to-bot conversations can continue without a separate exchange limit. Slopbot ignores its own live messages because its delivery path already stores them. Users can reply to another app’s message to ask Slopbot about it.

## participation
Mentions, replies and task-thread inputs bypass classification. Otherwise monitoring must be enabled. The classifier recognizes Slopbot, slop, bot, sb, ai and machine when addressed, rather than merely mentioned in discussion. Kev receives preceding messages and CURRENT, with addressed/respond/funny questions. Addressed probability requires 0.65; responding requires 0.5 when addressed or 0.9 otherwise. Funny requires 0.9 and selects 😂. A 404 uses the main model's JSON classifier, which can select 😂, 🤣, 😆, 😄 or 🤭. See decision_prompt and participation_prompt for exact current instructions. Fixed instructions precede changing message evidence.
Reactions are independent of text replies and do not need addressing. The admin reactions tool sets one frequency from 0 to 100, default 60. Zero disables reactions; 100 reacts to every classifier-selected suitable message. Intermediate values are the percentage chance per suitable message. There is no separate reaction cooldown or hourly cap. Existing explicitly disabled reactions remain off until frequency is changed. Disabling monitoring stops unsolicited reactions too. Reaction delivery failures do not prevent a text reply. Discord needs Add Reactions and Read Message History permissions. No extra model call generates an emoji.

## sandbox
The sandbox tool runs commands and reads/writes files in a remote PMServers E2B-compatible workspace. Actions are run, read, write, status and close. Each task thread has its own recorded sandbox ID; members in that task share the files. The first command or file write creates it. Commands and writes renew a ten-minute lifetime; status and reads do not. Expiration destroys files and processes; the next write starts fresh. Commands default to a 30-second timeout, maximum 60 seconds; tool output is limited to 16000 characters. No local host execution, bot files or environment credentials are forwarded. The PMServers base template has shell tools but our live check found no Python or Node. Inspect it and install required packages, or configure another template. Mutations are serialized and journaled. Lost command results are uncertain and are never blindly replayed. Reads remain available to inspect state. Provider API credentials are not available through bot_info. Discord shows tool progress and duration as usual. If E2B_API_KEY is absent, sandbox actions explain that configuration is needed. Arbitrary code and files remain untrusted evidence. Sandbox API and template compatibility must be verified against the configured service.
